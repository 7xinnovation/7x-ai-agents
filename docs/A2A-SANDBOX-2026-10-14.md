# The A2A sandbox for PMO — 14–15 October 2026

The Prime Minister's Office technical team asked for a staging environment they
can call with authorisation and test the PO Box registration and renewal end to
end. This is what was built, how it is wired, how to give someone access, and
how to check it.

## What it is

An **A2A 1.0 task doorway** in front of the existing chat engine, plus a
**developer portal** at `/developers` where an invited organisation creates its
own credentials, reads the documentation, tries calls in a console and sees its
request log.

Nothing changed inside the agent. Every A2A message becomes one turn of the
same engine the chat widget uses (`POST /api/chat`, called in-process), so an
integrator tests exactly what a customer gets: the journeys, the Emirates Post
tools, the guards, the payment handling, the audit trail. The doorway only
translates:

| A2A | Dialog |
|---|---|
| `contextId` | a conversation |
| task | one service request inside that conversation |
| `TASK_STATE_INPUT_REQUIRED` | the agent asked something, or is waiting for a payment (`metadata.awaiting`) |
| `TASK_STATE_AUTH_REQUIRED` | the agent needs the citizen signed in |
| `TASK_STATE_COMPLETED` | the order is recorded and paid, or the request was handed to a person |
| artifacts | `payment-request`, `service-outcome`, `escalation` |

The agent exposed is `po-box-sandbox`: a copy of `nxn-dialog` with its payment
bindings pointed at the mock gateway. The copy keeps PMO's test conversations
out of Emirates Post's transcripts and analytics.

## What is real and what is simulated

Real, from Emirates Post's staging systems: bundles, branches, opening hours,
prices, expiry dates. Simulated: the box reservation (`Rental/Select`), the
order (`Rental/Save`, `Guest/Renewal/Save`) and the payment confirmation
(`UpdatePayment`, `ConfirmPayment`). The order's payment is opened on our mock
checkout and settles through the signed webhook like a real gateway; the
simulated confirm reads that payment and answers paid only when it is. No real
box is rented and no money moves. References are prefixed `SBX-`.

The simulation runs only when the chat body carries `sandbox: true`, which only
the doorway sets. The demo persona and the `?mock=1` testers behave exactly as
before.

## Pieces

- `packages/core/src/a2a/protocol.ts` — the A2A 1.0 wire shapes, method names and error codes, from the specification.
- `apps/web/lib/a2a/` — `catalogue.ts` (exposed agents, Agent Card, the two extensions), `auth.ts` (OAuth 2.0 client credentials and API keys; hashes only), `tasks.ts` (task ↔ conversation, the engine call, state decisions, the settled-payment continuation), `blocks.ts` (the agent's fenced blocks as typed objects), `identity.ts` (the citizen's identity inside the task; sandbox personas), `service.ts`, `http.ts`, `log.ts`.
- Routes: `app/a2a/[agent]/route.ts` (JSON-RPC, Agent Card on GET), `app/a2a/[agent]/[...rest]/route.ts` (HTTP+JSON binding, `agent-card.json`, sandbox personas and payment settlement), `app/a2a/oauth/token/route.ts`, `app/.well-known/agent-card.json/route.ts`.
- Portal: `apps/web/lib/developer/` (session cookie `dlg_dev`, accounts, applications), `app/api/developers/*`, `app/developers/*`.
- Engine changes: `lib/mockPersona.ts` (`simulateNxnMockOp` takes a payable context), `lib/integrations.ts` (`mockPayable`), `app/api/chat/route.ts` (`sandbox` body flag), `app/api/payments/webhook/route.ts` and `status/route.ts` (call `onPaymentSettled`).
- Tables: `developer_accounts`, `developer_apps`, `a2a_tasks`, `a2a_requests` (schema in `packages/db/src/schema.ts`).

## Setting up an environment

From `apps/web`, in this order, before the code is deployed:

```
npx tsx scripts/create-a2a-tables-2026-10-14.ts --env <env file> --apply
npx tsx scripts/create-sandbox-agent-2026-10-14.ts --env <env file> --apply
```

Both are idempotent. The second one re-syncs the copy from `nxn-dialog`; run it
again whenever the NXN agent changes. No new app settings are needed:
`UAEPASS_MOCK_ALLOWED=1` (already on staging) is what lets the simulation run;
`A2A_TOKEN_SECRET` may be set to give the portal and the access tokens their
own secret, otherwise they derive one from `ADMIN_SESSION_SECRET`.

Done on staging on 15 October: tables created, `po-box-sandbox` created.

## Giving an organisation access

```
npx tsx scripts/provision-developer-account-2026-10-14.ts --env <env file> \
  --org "Prime Minister's Office" --name "<contact name>" --email <their email> \
  --base https://7xagents.7x-lab.com
```

It prints the sign-in link. Since 15 October there are no passwords: the
person enters their email and receives a six-digit code (ten minutes, five
tries, one use), sent through Resend from `no-reply@7x-lab.com` using the
staging settings `RESEND_API_KEY_DEVELOPERS` and `EMAIL_FROM_DEVELOPERS`. They
then create an application in the portal. The application
has a `client_id` and `client_secret` (exchange them at `/a2a/oauth/token`) and
an API key (`X-API-Key`), shown once. Rotation invalidates the old pair and
every token issued before it. We never hold their password; only hashes of the
credentials are stored. Re-running the script for the same email re-invites.

Accounts on staging: `ceo@platx.digital` (Prime Minister's Office, created 15
October) and `a2a-qa@7x.ae` (our own verification). The earlier placeholder
`pmo-technical-team@sandbox.7x.ae` is deactivated.

## Checking it

```
npx tsx scripts/test-a2a-sandbox-2026-10-14.ts
npx tsx scripts/test-a2a-sandbox-2026-10-14.ts --base https://7xagents.7x-lab.com --client-id <id> --secret <secret>
```

Part one needs no server: protocol invariants, the Agent Card, the block
parser, the simulation's shapes. Part two drives a deployment: discovery, the
token endpoint, every error code, a guest question, a signed-in renewal
through to the payment request, the sandbox settlement, the task completing by
itself with a `service-outcome` artifact, listing, cancelling, the REST binding
and streaming. 48 checks — all green locally and on staging (15 October, after
the deploy of f1658ca).

Also on staging, 15 October: a scripted **new personal PO Box rental** run as
the signed-in persona went from "I want to rent a new personal PO Box in Dubai"
through bundle, branch, box number, term, no agent, key collection, the contact
confirmation, the order summary and the before-payment toggles to a
`payment-request` of AED 370 (rental 300 plus the sandbox registration fee 70),
was settled through the sandbox endpoint, and completed by itself: order
`SBX47484829`, a `service-outcome` artifact with the payment as paid and a
receipt link. Eleven turns, about six minutes.

By hand: `GET https://7xagents.7x-lab.com/.well-known/agent-card.json` must
answer the card; `/developers/docs` the documentation.

## Decisions worth knowing

- **The settled-payment turn.** The widget's `paymentSettled` directive tells a
  journey that saves through Emirates Post to call its save tool, which after
  a gateway payment would open a second order. For an order on the gateway the
  doorway therefore sends what the widget's pay button sends when the customer
  returns ("I have completed the payment on the Emirates Post page…"), and the
  agent calls the confirm tool.
- **One turn at a time per task.** A second message while one is running is
  refused with `-32004`, not interleaved. A turn that runs past 280 seconds is
  given up on.
- **A transient engine error does not fail the task.** It stays
  `INPUT_REQUIRED` with the apology and a `warning` in the data part; the
  client sends the same message again. `TASK_STATE_FAILED` means the agent is
  not configured on the host.
- **Document uploads** cannot be sent over the doorway (file parts are refused
  with `-32005`). They are needed only when adding an authorised agent.
- **Local testing is unreliable for long flows**: the Mac's connection to the
  Neon database and to the model endpoint drops (socket timeouts, one request
  took 64 minutes). Verify on staging.
