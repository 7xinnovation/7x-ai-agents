## FB-1564 — the AI communication needs to be more human

**What changed.** The persona described the agent as "government-grade in tone",
which is what it was delivering. It now describes a person. Both journeys also
carry a rule that names the specific habits to drop (bureaucratic openers,
restating your message back at you, filler) and requires contractions and short
sentences. Accuracy is still a hard constraint — sounding friendlier is not
licence to soften a requirement or invent a timeline.

**How to test.**
1. Open the EPGL agent and type *"I want to apply for a new courier licence"*.
2. Read the reply out loud. It should sound like a colleague: contractions
   ("you'll", "let's"), one idea per sentence.
3. Check none of these appear anywhere in the conversation: "Kindly be
   informed", "Please be advised", "as per the above", "Noted with thanks",
   "Dear Applicant". No emoji.
4. Upload a document that gets rejected (e.g. a random PDF as the trade
   licence). The refusal should be one plain sentence plus the fix — not an
   apology paragraph.
5. Switch to Arabic and repeat step 1. The Arabic should read naturally, not as
   a literal translation of English. Brand names (EPGL, IDEP) stay in Latin
   script — that is intended.

**Expected.** Warm and direct throughout, with no drop in precision about
documents, timelines or fees.

## FB-1565 — next steps should be clear rather than prompted by the applicant

**What changed.** Both journeys now require every message to end by naming what
happens next; the journey opens by stating its stages; waits on EPGL are
explained (what will happen, roughly when, what you receive) instead of being
left for you to ask about; and choices are offered as buttons rather than open
questions.

Separately, the agent used to attach several upload boxes at once at the
opening turn. The agent is now capped at **one upload control per message**
(`uploadsPerMessage: 1`), so you are only ever asked for one document at a time.

**How to test.**
1. Start a new licence application. The first reply should tell you the stages
   before asking anything.
2. At every point in the conversation, check you never have to ask "what now?" —
   each message ends with a question, a button, or an upload box.
3. Count the upload boxes in any single message: there must never be more than
   one.
4. Upload the trade licence. The reply should confirm what was read **and** name
   the next item in the same message.
5. Ask *"what happens after I submit?"* — you should already have been told; the
   answer should match what it said earlier (review ~2 business days → payment
   request → licence issued).
6. Repeat 1–4 in Arabic.

**Known limitation, called out honestly:** the model still sometimes *writes*
two upload blocks in the opening message. Only the first is now rendered, so
you see one box. This behaviour pre-dates this round — it was verified against
the previous agent definition and behaved the same way — and the cap is what
fixes what the customer sees.

## FB-1566 — only the client's preferred contact details should be editable

**What changed.** The pencil in the application panel used to appear on every
text field, including values read off your trade licence. It now appears only
on contact details. This is enforced by the server, not just hidden in the UI —
a request to change a locked field is rejected with `field_not_editable`.

| Journey | Editable | Locked |
|---|---|---|
| New licence | contact person, contact email, contact phone, designation, owner contact number | company name (EN/AR), trade licence number and expiry, initial approval number, emirate, region, street address, PO Box, activity codes, owner name / nationality / passport / Emirates ID |
| Renewal | accountant name, email, phone | postal licence number, trade licence number and expiry, trade names, financial year, all four quarterly leviable-income figures |

The agent is also told not to overwrite a document-sourced value just because
you say a different one. If we **misread** the document it will still correct it
to what the document says; if the **document itself** is wrong or out of date,
it asks for a corrected upload rather than quietly changing the application.

**How to test.**
1. Run a new licence application far enough to upload a trade licence, so the
   panel fills with extracted values.
2. Hover each row in the application panel. A pencil should appear **only** on
   the contact fields.
3. Edit the contact email — it should save and show the new value.
4. Try to change the company name or trade licence number: there should be no
   pencil at all.
5. In chat, say *"my company name is actually Something Else LLC"*. The agent
   should not silently change it — it should check against the document and ask
   for a corrected upload if the document is wrong.
6. In chat, say *"you read the licence number wrong, the document says 12345"*.
   Here it **should** correct the field, because that is a misread.
7. Renewal: confirm the pencil is on the accountant contact only.

**Note for review:** the quarterly leviable-income figures are locked by this
rule too, since they are not contact details. You can still change them by
telling the agent. If you would rather those stay directly editable, that is a
one-line change — say the word.

## FB-1567 — pin the physical address on Google Maps

**What changed.** A map with a draggable pin can now be shown in the EPGL
conversation. Confirming the pin sends the address, the coordinates and a
**Google Maps link**, and the coordinates are stored on the application in a new
"Pinned location (map)" field.

The map picker itself is Mapbox — the same one already used for the branch
finder, so there is one map library and one token. What you asked for
(the location openable on Google Maps) is delivered as the google.com/maps link
that travels with the application. If EPGL specifically requires the *picker* to
be Google Maps, that needs a Google Maps API key and is a separate change.

The picker is now bilingual — its buttons and status messages appear in Arabic
in an Arabic session, and the address it reads back is geocoded in Arabic.

**How to test.**
1. Start a new licence application and say *"can you show me the map so I can
   pin our premises?"* — the map should appear **in that same reply**, not be
   promised for later.
2. Drag the pin, or tap the map to move it. The address underneath should update
   as you move it.
3. Tap "Use this location". Your message should show the address, the
   coordinates and a Google Maps link. Open the link — it should land on the
   pin.
4. Check the application panel: "Pinned location (map)" should hold the
   coordinates and link.
5. Deny the browser location permission and try again — it should fall back
   gracefully and let you type the address instead. It must not get stuck or ask
   twice.
6. Switch to Arabic and repeat. Every label on the map widget should be Arabic.

**Normal flow:** in a real application the map appears once the trade licence has
pre-filled the address. Asking for it directly (step 1) works at any point.

## What this round did not change

- Nothing on the NXN agent. Both new controls are opt-in per agent: NXN declares
  no editability flags and no upload cap, so it behaves exactly as before
  (including its deliberate Emirates ID front + back pair in one message).
- The pinned coordinates are stored on the application but are **not** sent to
  Salesforce — the contract has no field for them. If EPGL wants the coordinates
  on the Account record, that is an addition to the Salesforce API request
  already raised (see `reports/EPGL-Salesforce-API-Requests.md`).
- FB-1567 is wired into the **new licence** journey. The renewal journey has no
  address field, so there is nowhere to put a pin; say if renewals should
  capture a changed address too.
